# Verifying code and tests produced by AI coding agents: 2024-2026 literature, read against ElevenPowers

Read on 2026-11-22. "Abstract-only" means only the arXiv /abs/ page was read. "HTML read" means the arXiv /html/ full text was fetched. "Snippet-grade" means the figure came from a search-engine summary and was not checked against the paper; treat it as a lead, not a citation. No PDFs were used.

## (1) How often agent patches are inadequately tested or overfit

### Takeaway
Several independent audits put the share of "resolved" SWE-bench patches that are wrong or only weakly checked at roughly 7-33%, depending on the method. Benchmark tests are also often too narrow: OpenAI found implementation-pinning tests in 35.5% of the hard Verified tasks it audited. When agents' own tests are used as the oracle, 22-33% of patches that pass them fail the hidden tests. When agents choose whether to write tests at all, the choice barely changes the outcome.

### Cited Findings
**Plausible-but-wrong patches in SWE-bench evaluations**
- Wang, Pradel and Liu, "Are 'Solved Issues' in SWE-bench Really Solved Correctly?" (arXiv 2503.15223, v2 Sep 2025; abstract-only). SWE-bench validation lets "7.8% of all patches … count as correct while failing the developer-written test suite". With PatchDiff (differential test generation against the gold patch), "29.6% plausible patches induce different behavior than the ground truth patches". Of the divergences, 46.8% come from similar but divergent implementations and 27.3% from patches that "adapt more behavior" than the gold patch. On manual inspection, "28.6% of behaviorally divergent patches are certainly incorrect". Together these inflate reported resolution rates "by 6.2 absolute percent points". The study covers three tools on SWE-bench Verified. — [arXiv:2503.15223](https://arxiv.org/abs/2503.15223)
  - The HTML version (per a search summary, snippet-grade) attributes the 7.8% to SWE-bench running only the test files the PR modified. — [arXiv html 2503.15223v2](https://arxiv.org/html/2503.15223v2)
- Yu, Zhu, He and Kang, "UTBoost: Rigorous Evaluation of Coding Agents on SWE-Bench" (ACL 2025; abstract-only). LLM-generated augmenting tests found "36 task instances with insufficient test cases" and "345 erroneous patches incorrectly labeled as passed". This affected "40.9% of SWE-Bench Lite and 24.4% of SWE-Bench Verified leaderboard entries" and caused "18 and 11 ranking changes". — [arXiv:2506.09289](https://arxiv.org/abs/2506.09289)
- Aleithan et al., "SWE-Bench+" (arXiv 2410.06992, Oct 2024; abstract-only). The study is on SWE-Agent+GPT-4 resolved patches: "32.67% of the successful patches involve cheating" (the solution was in the issue or comments), and "31.08% of the passed patches are suspicious patches due to weak test cases". After filtering, resolution fell "from 12.47% to 3.97%". This is an older, weaker agent, so the rates should not be carried over to current models. — [arXiv:2410.06992](https://arxiv.org/abs/2410.06992)
- OpenAI, "Why we no longer evaluate SWE-bench Verified" (23 Feb 2026; full page read). OpenAI audited 138 Verified problems that o3 did not solve consistently over 64 runs (a "27.6% subset"), each reviewed by at least six engineers. "At least 59.4% of the audited problems have flawed test cases that reject functionally correct submissions." Of the audited tasks, 35.5% have "strict test cases that enforce specific implementation details", 18.8% test "additional functionality that wasn't specified", and 5.1% have miscellaneous issues. The post also gives contamination evidence: every frontier model tested could reproduce gold patches or verbatim problem details for some tasks. OpenAI recommends SWE-bench Pro instead and estimates about 30% of Pro tasks are broken (the 30% is from a search summary, snippet-grade). Caveat: the sample is the hard tail, not the whole benchmark. — [OpenAI](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)
- Epoch AI's benchmark review (dated 3 Sep 2026, per a search summary, snippet-grade) gives the verdict "Flawed", with over 20% of questions having scoring issues. The audit was partial. — [Epoch AI](https://epoch.ai/benchmarks/swe-bench-verified/review)

**Agent-written tests: adequacy and value**
- Mündler, Müller, He and Vechev, "SWT-Bench" (arXiv 2406.12952, v3 Feb 2025; HTML read). Fail-to-pass reproduction success on SWT-Bench-Lite (276 issues): SWE-Agent+ 18.5% (F→P 19.2%), SWE-Agent 15.9%, LIBRO 14.1%, aider 12.7%, AutoCodeRover 9.1%. Pass-to-pass tests ("correct but unhelpful", i.e. vacuous) make up 7.2-10.1% of agent tests, against 11.2% for golden tests. Change coverage is 26.5-27.8% for agents against 72.0% for golden tests. An "ideal ensemble of the best four methods" solves 71% more than the best single method. — [arXiv html 2406.12952v3](https://arxiv.org/html/2406.12952v3)
- Chen et al., "Rethinking the Value of Agent-Generated Tests for LLM-Based Software Engineering Agents" (arXiv 2602.07900, v2 Apr 2026; HTML read, first 100k characters). Setting: mini-SWE-agent, SWE-bench Verified, testing optional. Test-writing rates: Claude Opus 4.5 83.0%, Gemini 3 Pro 61.6%, GPT-5.2 0.6%, Kimi K2 97.4%, MiniMax M2 98.6%, DeepSeek v3.2 89.2%. GPT-5.2 writes almost no tests and still resolves 71.8%, against 74.4% for Opus 4.5. Resolved and unresolved runs write tests at similar rates, e.g. Opus 84.4% vs 78.9%. Prompt interventions changed test writing on 37-75% of tasks, but no model's resolution changed significantly: Gemini −1.0 pp (p=0.522), Kimi −2.6 pp (p=0.228), DeepSeek −1.8 pp (p=0.435), GPT-5.2 0 pp. About 83.2% of tasks kept the same outcome. Discouraging tests cut input tokens by 33-49%. Agent "tests" are mostly prints (Opus: 25.00 prints vs 5.16 assertions per resolved task). Relational assertions are 3-8% of assertions. The paper does **not** measure vacuity or reproduction. — [arXiv html 2602.07900v2](https://arxiv.org/html/2602.07900v2)
- Ahmed, Ganhotra, Shinnar and Hirzel, "Investigating Test Overfitting on SWE-bench" (arXiv 2511.16858, v3 Apr 2026; HTML read). Setting: Agentless patches checked against e-Otter++ generated tests on TDD-Bench Verified. Of patches passing the generated test, 21.8% (Claude-3.7-Sonnet, 50/229) and 33.0% (GPT-4o, 58/176) fail the hidden gold or regression tests. Refining patches against the generated tests raised overfitting to 25.5% and 35.9%, and 14 of the 22 newly passing refined patches were wrong. Hiding the tests from the model reduced overfitting only partly. Even refining against the golden tests broke regression tests in 5.8% (Claude) and 11.3% (GPT-4o) of cases. Overfitted patches had lower coverage (mean 0.90 vs 0.95). The paper proposes coverage as an early warning but does not test it. Note: the paper's denominator is the instances passing the generated test, not all instances. — [arXiv html 2511.16858v3](https://arxiv.org/html/2511.16858v3)
- Lu et al., "SWEPatchTest" (arXiv 2610.18004, Oct 2026; abstract-only). Covers 619 tasks and 82,579 agent-trajectory candidate patches. The best test-generation configuration reaches a Joint Validation Rate of only 9.21%: on the same task, the suite must reproduce the issue, accept the correct patches and reject the incorrect ones. Reproduction alone succeeds on 59.29% of tasks. — [arXiv:2610.18004](https://arxiv.org/abs/2610.18004)

**Test-first**
- "TDD-Bench Verified" (arXiv 2412.02883, Dec 2024). Per a search summary (snippet-grade), GPT-4o wrote fail-to-pass tests from the issue alone, before any fix, 23.6% of the time. — [arXiv html 2412.02883v1](https://arxiv.org/html/2412.02883v1)
- "TDFlow" (arXiv 2510.23761, v2 Jan 2026). Per a search summary (snippet-grade): 94.3% on SWE-bench Verified when given the human-written tests, 69.8% with self-generated tests, and only 7 cases of test hacking in manual review. — [arXiv html 2510.23761v2](https://arxiv.org/html/2510.23761v2)

### Inferences
- ElevenPowers' vacuity measure (no test fails with the change reverted) is the same idea as SWT-bench's pass-to-pass / fail-to-pass split. The literature measures it for issue-reproduction tests, not for "whatever the agent left behind". The 84% vs 37% held-out result therefore measures something the field has not published, and should be described as such rather than compared directly with SWT-bench rates.
- The 2602.07900 result (test writing moves outcomes by ≤2.6 pp, not significant) matches ElevenPowers' own finding: superpowers users already write tests, and the v3 run found no measured benefit. Getting agents to write *more* tests is not where the value lies. The value would come from tests that *discriminate*, and even 2602.07900 does not measure that.
- OpenAI's 35.5% "implementation-detail" tests in gold suites matches ElevenPowers' finding that raw mutation survivors produce implementation-pinning tests. Even human-written benchmark tests over-constrain. Any adequacy push needs a guard against pinning, not just against vacuity.
- The 2511.16858 result is a direct warning for any feature that hands agent-generated tests back to the agent as a target. Refinement raised overfitting.

### Gaps
- Found no published rate of vacuous tests left in place by general-purpose agents (Claude Code, Cursor, etc.) on real repositories. SWT-bench measures dedicated reproduction-test generation.
- Found no controlled test-first vs test-after comparison for LLM agents in which correctness is the outcome. TDFlow's high figures depend on supplied human tests.
- The full UTBoost and PatchDiff per-tool breakdowns were not read (abstract-only).

## (2) Which signals best predict a wrong-but-passing patch

### Takeaway
The strongest signals published are differential: a test on which the candidate behaves differently from a reference (the gold patch, other candidate patches, or the pre-change code). After that come independently generated issue-reproduction tests used as a filter, which give high precision at low recall. Coverage is weakly associated with overfitting. Critic accuracy offline does not predict whether acting on the critic helps.

### Cited Findings
- **Differential testing against a reference.** PatchDiff separated 29.6% of plausible patches from the gold patch. Only 28.6% of those were confirmed incorrect, so divergence alone is a "suspicious" flag, not a verdict. — [arXiv:2503.15223](https://arxiv.org/abs/2503.15223). UTBoost uses the same gold-vs-candidate idea. — [arXiv:2506.09289](https://arxiv.org/abs/2506.09289)
- **Independent issue-derived tests as a filter.** Otter / Otter++ (ICML 2025; HTML read). Dropping patches on which all five Otter++ tests fail gave 65-92% precision at 30-41% recall across 22 SWE-bench Verified leaderboard systems. One example went from 60.8% to 91.9% precision at 33% recall. The SWT-bench SWE-Agent+ filter reached 47.8% precision at about 20% recall (described as "more than doubles" SWE-Agent's precision). CodeT-style ranking added only about 2%. Cost was about $0.06-0.09 per instance with GPT-4o. Fail-to-pass rates: 37.0% on TDD-Bench-Verified and 29.0% on SWT-bench Lite for Otter++. — [arXiv html 2502.05368v2](https://arxiv.org/html/2502.05368v2); [arXiv html 2406.12952v3](https://arxiv.org/html/2406.12952v3)
- **Treat the diff as a mutant.** Meta's "Just-in-Time Catching Test Generation" (arXiv 2601.22832, Jan 2026, FSE 2026 industry track; abstract-only, plus search summary). The "dodgy diff" workflow treats each diff as a mutant of its parent and generates tests that separate the two. An intent-aware variant has an LLM infer the diff's intent, list its "risks", and build mutants from those risks (snippet-grade for the workflow description). Over 22,126 generated tests, code-change-aware methods improve candidate catch generation "4x over hardening tests" and "20x over coincidentally failing tests". LLM assessors "reduce human review load by 70%". Of 41 candidate catches reported to engineers, 8 were confirmed true positives, 4 of them serious. — [arXiv:2601.22832](https://arxiv.org/abs/2601.22832); see also [Meta Engineering, Oct 2026](https://engineering.fb.com/2026/10/29/security/catching-bugs-before-they-land-jittestings-human-on-the-loop-approach-at-full-scale/) (not read)
- **Coverage.** Overfitted patches had median coverage below 0.8 vs 1.0 for correct ones (Claude, 2511.16858). This is suggestive only: the authors do not test it as a predictor. — [arXiv html 2511.16858v3](https://arxiv.org/html/2511.16858v3)
- **Execution-free critics.** 2501.16655 (Jan 2025; per a search summary, snippet-grade): test-aware LLM critics predict executability at F1 91.6% and build status in 84.8% of SWE-bench instances. They assume access to the gold test patch. — [arXiv html 2501.16655v1](https://arxiv.org/html/2501.16655v1)
- **Critic accuracy is not intervention value.** Vasudev et al. (arXiv 2602.03338, Feb 2026; abstract-only). A binary LLM critic with "AUROC 0.94" offline caused a "26 percentage point (pp) collapse on one model" and about 0 pp on another. Intervention hurt high-success tasks (0 to −26 pp) and helped high-failure ALFWorld by +2.8 pp (p=0.014). The authors propose a 50-task pilot before deployment. Benchmarks were HotPotQA, GAIA and ALFWorld (per search summary), not coding. — [arXiv:2602.03338](https://arxiv.org/abs/2602.03338)

### Inferences
- ElevenPowers' change-reversion check is the deployment-time version of PatchDiff and Meta's "dodgy diff". The reference is the parent commit rather than a gold patch. This is well-founded and has an industrial precedent to cite as its borrow: Meta JiT treats the diff as the mutant.
- Divergence needs a second judgement. PatchDiff confirmed only 28.6% of divergences as bugs, and Meta's JiT needed LLM assessors plus humans to reach 8 true catches out of 41. A raw "this test discriminates / does not" signal will be noisy as a correctness verdict. It is more defensible as an adequacy signal, which is how ElevenPowers uses it.
- The high-precision, low-recall filter (Otter) relies on tests written *from the issue, without seeing the patch*. ElevenPowers' tests are written by the same agent after the patch. Independence of the oracle seems to be the property that buys precision.

### Gaps
- Found no head-to-head study ranking mutation score, coverage, reversion-discrimination and LLM-judge as predictors of wrong-but-passing agent patches on the same data. This is an open question ElevenPowers could answer with its own corpus.
- No study found that measures whether *pseudo-tested methods* in a patch predict patch incorrectness.

## (3) Does mutation testing / adequacy evidence help human or model reviewers?

### Takeaway
Industrial evidence (Google, Meta) shows that developers act on surfaced mutants and on mutation-guided tests, and write more tests. No study found shows that adequacy evidence makes a *reviewer* better at spotting wrong code. Controlled studies of AI-assisted review show anchoring: reviewers focus on the flagged locations and find more low-severity issues but not more high-severity ones. That is consistent with ElevenPowers' non-significant 20/21 vs 18/21.

### Cited Findings
- **Google, mutation testing in code review.** Petrović, Ivanković, Fraser and Just, "Does mutation testing improve testing practices?" (ICSE 2021; abstract-only). The study covers "almost 15 million mutants" and finds "developers using mutation testing write more tests". The abstract gives no effect sizes. — [arXiv:2103.07189](https://arxiv.org/abs/2103.07189)
- Further Google figures, all snippet-grade from search summaries: diff-scoped mutants surfaced in review, used by more than 24,000 developers on more than 1,000 projects, with about 2M surfaced mutants (TSE 2021) — [UW copy of TSE 2021](https://homes.cs.washington.edu/~rjust/publ/practical_mutation_testing_tse_2021.pdf). Earlier figures: 1.1M mutants and 150k actionable findings, with reported usefulness rising from 20% to 80% after feedback-driven suppression of unproductive mutants — [Google Research, "State of Mutation Testing at Google"](https://research.google/pubs/state-of-mutation-testing-at-google/). The location of 64% of surfaced mutants changes during review (ICSE 2023) — [UW copy](https://homes.cs.washington.edu/~rjust/publ/mutation_testing_resolution_icse_2023.pdf). These are pre-2024 but foundational to diff-scoped mutation.
- **Meta, mutation-guided LLM test generation (ACH).** Foster et al. (arXiv 2501.12862, FSE 2025 industry; abstract-only). ACH was applied to 10,795 Android Kotlin classes, producing 9,095 mutants and 571 privacy-hardening tests. "Engineers accepted 73% of its tests, judging 36% to privacy relevant." An LLM equivalent-mutant detector achieved "precision of 0.79 and a recall of 0.47 (rising to 0.95 and 0.96 with simple pre-processing)". The mutants are *concern-targeted* (privacy faults described in plain text), not syntactic operators. — [arXiv:2501.12862](https://arxiv.org/abs/2501.12862)
- **Human reviewers with AI-generated reviews.** Tufano et al., "Deep Learning-based Code Reviews: A Paradigm Shift or a Double-Edged Sword?" (ICSE 2025; abstract-only). In a controlled experiment with 29 experts (50+ hours), "Reviewers tend to focus on the code locations indicated by the LLM". With an automated review they found more low-severity issues but not more high-severity ones, with no time saving and no confidence gain. — [arXiv:2411.11401](https://arxiv.org/abs/2411.11401)
- **Human+LLM critic teams.** McAleese et al., "LLM Critics Help Catch LLM Bugs" (OpenAI, Jun 2024; abstract-only). Model critiques were "preferred over human critiques in 63% of cases". "Human-machine teams of critics and contractors catch similar numbers of bugs to LLM critics" while hallucinating less. Hallucinated bugs "could mislead humans into making mistakes they might have otherwise avoided." — [arXiv:2407.00215](https://arxiv.org/abs/2407.00215)
- **Model reviewers on their own.** Yang et al., CRBugBench (Microsoft, arXiv 2610.13668, Oct 2026; abstract-only). The best code-review agent (claude-opus-5 + copilot-cli) catches 71.9% of bugs within its top-5 comments, up from 47.7% for opus-4.6 five months earlier. Exploration-nudging prompts add up to 5.8% at about 10% higher cost. Performance drops "sharply" on proprietary repositories, with no figures given. — [arXiv:2610.13668](https://arxiv.org/abs/2610.13668)
- **LLM reviewer biases** (search summaries, snippet-grade): framing the prompt skews LLM security review, with false negatives more affected — [arXiv html 2603.18740](https://arxiv.org/html/2603.18740v1). LLM reviewers over-flag correct code as failing requirements — [arXiv html 2603.00539](https://arxiv.org/html/2603.00539v1). Automation bias is named among the biases in LLM-assisted development (ICSE '26; findings not read) — [arXiv 2601.08045](https://www.arxiv.org/pdf/2601.08045).

### Inferences
- ElevenPowers' reviewer experiment (20/21 vs 18/21) sits where the literature predicts. Strong model reviewers are already near ceiling on small diffs (CRBugBench 71.9% top-5 and rising). Extra evidence tends to redirect attention rather than add detection (Tufano). A ceiling effect at n=21 cannot show a gain. A test of whether adequacy evidence helps needs harder, larger diffs where the diff-only reviewer is well below ceiling, plus a measure of misdirection (false flags introduced by the report), not only catches.
- The industrial wins (Google, Meta) come from evidence aimed at the *author or test writer* (write a test for this mutant / accept this test), not at the reviewer's verdict. That supports positioning ElevenPowers' report as author-side guidance rather than a reviewer aid.
- Meta ACH and JiT both filter mutants before anyone sees them: equivalent-mutant detection, concern targeting, LLM assessors cutting review load by 70%. Google needed suppression of unproductive mutants to reach high usefulness (snippet-grade). This independently matches ElevenPowers' finding that raw survivors make agents write pinning tests. The borrowable fix is filtering and targeting, not a different instrument.

### Gaps
- Found no controlled study in which reviewers (human or LLM) receive mutation or coverage evidence vs no evidence and detection of incorrect code is the outcome. This is a real gap in the literature, not only in this search.
- Google's papers give developer-behaviour outcomes (more tests). None found measures defect escape against a control.

## (4) Promising techniques ElevenPowers does not yet use

### Takeaway
The best-supported additions are: (a) independent oracle tests written from the issue or intent without seeing the patch (Otter), used as a high-precision filter; (b) intent- or risk-targeted mutants plus LLM equivalent-mutant filtering, instead of raw operator survivors (Meta ACH/JiT); (c) agentic property-based tests (Anthropic-affiliated work on Claude Code). Specification inference (postconditions) is real but low-yield. Any critic or intervention should pass a small pilot before it ships.

### Cited Findings
- **Issue-derived, patch-blind reproduction tests + ensembles.** Otter++ (see (2)). Ensembles of 5 raise fail-to-pass from 31.4% to 37.0% on TDD-Bench-Verified, at about $0.09 per instance. — [arXiv html 2502.05368v2](https://arxiv.org/html/2502.05368v2). On SWT-bench, an ideal four-method ensemble solves 71% more than the best single method. — [arXiv html 2406.12952v3](https://arxiv.org/html/2406.12952v3)
- **Risk/intent-targeted mutants and LLM equivalent-mutant detection.** Meta ACH: precision 0.95 and recall 0.96 for equivalence detection after pre-processing, and 73% test acceptance — [arXiv:2501.12862](https://arxiv.org/abs/2501.12862). Meta JiT intent-aware mutants — [arXiv:2601.22832](https://arxiv.org/abs/2601.22832). Tian et al., "LLMs for Equivalent Mutant Detection: How Far Are We?" (ISSTA 2024 Distinguished Paper; per a search summary, snippet-grade): 3,302 Java mutant pairs, LLM methods compared with ten existing EMD techniques, with fine-tuned code embeddings performing best. A 2026 extension covers C. — [arXiv:2408.01760](https://arxiv.org/abs/2408.01760); [arXiv:2607.00511](https://arxiv.org/abs/2607.00511)
- **LLM-generated mutants.** Ma et al. (arXiv 2406.09843; snippet-grade): LLM mutants reach a 76.47% detection rate vs 44.15% for rule-based mutants, but with worse non-compilability, duplication and equivalence rates. — [arXiv html 2406.09843v5](https://arxiv.org/html/2406.09843v5)
- **Pseudo-tested statements, not only methods.** Maton, Kapfhammer and McMinn (2024; snippet-grade): statement-deletion XMT found 722 pseudo-tested statements, of which 48% lie outside pseudo-tested methods and would be missed by method-level (Descartes-style) analysis. — [White Rose eprint](https://eprints.whiterose.ac.uk/id/eprint/216881)
- **Agentic property-based testing.** Maaz, DeVoe, Hatfield-Dodds and Carlini (arXiv 2510.09907, NeurIPS 2025; search summary, snippet-grade). A Claude Code agent writing Hypothesis tests across 100 Python packages: 56% of reports were valid bugs and 32% were reportable. For the top-21 ranked reports, the figures were 86% and 81%. 3 patches were merged, including in NumPy. — [arXiv:2510.09907](https://arxiv.org/abs/2510.09907v1). A follow-up (arXiv 2610.34487, snippet-grade) found 28 real bugs among 50 reviewed alarms. — [arXiv:2610.34487](https://arxiv.org/pdf/2610.34487)
- **Specification inference.** nl2postcond (Endres et al., FSE 2024; snippet-grade): GPT-4 produced bug-discriminating postconditions for up to 47/525 (9%) Defects4J bugs. — [arXiv:2310.01831](https://arxiv.org/abs/2310.01831v2). A follow-up 7B model caught about 11% of bugs (snippet-grade). — [arXiv html 2507.10182](https://arxiv.org/html/2507.10182v1)
- **Small trained critics can help coding agents.** "Steer, Don't Solve" (arXiv 2606.21811, v2 Sep 2026; abstract-only). Fine-tuned 4B/8B critics improved the resolved rate of GLM-4.7-Flash by 16.0% and GPT-OSS-120B by 14.4% on SWE-bench Verified, and halved GPT-OSS-20B per-example cost ($0.07 to $0.03). A search summary of the body (snippet-grade) says an *untrained* critic fired almost only on "Verification Failures" (330/354) and pulled agents off self-review on tasks they would have solved. — [arXiv:2606.21811](https://arxiv.org/abs/2606.21811)
- **Pre-deployment pilot for interventions.** A 50-task pilot to decide whether to intervene at all. — [arXiv:2602.03338](https://arxiv.org/abs/2602.03338)
- **Human-refined rubrics for LLM patch judging** (arXiv 2511.10865, snippet-grade): rubric-guided LLM judges reach "moderate to substantial" agreement with humans. — [arXiv:2511.10865](https://arxiv.org/abs/2511.10865v1)

### Inferences
- **Most actionable:** pair change-reversion with a *patch-blind* oracle. A sub-agent writes a reproduction test from the task statement before or without seeing the diff. The existing reversion check then confirms that it fails on the parent and passes on the change. This combines ElevenPowers' instrument with the one technique shown to give high-precision patch filtering (Otter: 60.8% to 91.9% precision).
- **Replace raw survivors with filtered, targeted mutants:** LLM equivalent-mutant filtering, plus mutants built from the task's stated intent or risks (Meta JiT), handed to the agent as "behaviour the task implies should be pinned". Raw survivors are what the project observed producing implementation-pinning tests. Both Meta and Google filter before exposure.
- **Statement-level pseudo-tested analysis** is a cheap extension of the existing Descartes-style instrument, with evidence that method-level analysis misses about half the cases (snippet-grade).
- **Property-based tests** are the strongest independent-oracle technique with Claude Code evidence. They also resist implementation pinning by construction, because properties state behaviour rather than values. That addresses the pinning failure directly.
- Given v3's null-to-negative result and 2602.03338, any new intervention should be gated by a small pilot on the corpus, with the success-rate effect, not offline accuracy, as the gate metric.

### Gaps
- Found no study that applies inferred specifications or PBT specifically to *validating agent patches* (as opposed to finding bugs in libraries).
- Found no LLM-based detector of pseudo-tested methods, nor any study combining extreme mutation with LLM test generation.
- Several 2026 items (SWEPatchTest, CRBugBench, Steer-Don't-Solve, JiT) are recent preprints read at abstract level only. Their methods have not been independently reproduced.
