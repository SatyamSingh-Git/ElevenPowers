# A working pipeline needs evidence

2026-10-01. The next milestone followed the previous delivery: test-strength
findings were built, but the largest usability uncertainty was whether the
complete integration worked in an ordinary project and host session.

The implementation stayed project-independent. Readiness now composes one fresh
portable report with native configuration, runtime lookup, startup, edit delivery,
command capture, current declared verification and completion. Callback timing
and hashed task/session/receipt links collect automatically, within explicit
history limits. Health reads run no project check, import no optional engine,
launch no host and write no state. Pipeline health does not turn UNVERIFIED task
claims into VERIFIED ones.

The exercise became reproducible as tooling, not a checklist confined to Snag.
Explicit preparation creates a new Git repository, unchanged boundary tests,
intentionally faulty Python or JavaScript source, owned native wiring and
instructions. Real unittest/Node producers fail before the source correction and
pass afterward. A wait marker makes actual interruption testable. Inspection
requires unchanged contracts, the current generation and task/session, native
pass/fail/incomplete history, fresh verification and completion. Preparation and
replay remain waiting.

Ten actual language/launcher combinations passed. They exercise all five adapters
as child processes and run real tests, including interruption and stale/rerun.
They are contract controls. The machine had Claude Code 2.1.286 and Codex CLI
0.159.2; the other executables were absent. A new real Claude 2.1.286 session
processed SessionStart in the disposable exercise without a model prompt; browser
access was declined. Readiness showed startup observed while the full pipeline
and acceptance remained waiting. One retained 117.32 ms callback sample excludes
launcher startup and is not representative session latency. No paid evaluation
was launched. Startup evidence is still only startup evidence.

The fresh reviewer found five defects the initial controls had not covered:

- A passing individual pytest test with the suite's timestamp could hide the
  failing aggregate command receipt and make `--check` succeed.
- A malformed pending patch record escaped the final health read as a traceback.
- Corrupt project JSON could become silent defaults and leave health observed.
- A successful Stop erased the impact of an unresolved pre-tool phase error.
- The exercise test could change after the nested health read but before
  acceptance returned, while its earlier immutable check still said true.

Every reproduction was observed RED before correction and GREEN afterward.
Aggregate outcomes now govern declared verification, damaged state is actionable,
same-phase recovery is required and acceptance rechecks its bounded contract.
Earlier boundary controls also corrected late deadlines, completion ordering,
moving edit diagnostics and oversized timing summaries. These are reasons to use
focused adversarial controls while building, with a broad integration check at
the delivery boundary, rather than repeat the entire suite after each small edit.

The user requested 17 incremental pushes. Runtime and corrections were published
as ready, followed by architecture, all six guides, delivery records and the
final README/provenance publication. Exact verification belongs in the
[dated record](../docs/validation/2026-10-01-project-health.md). The next milestone
is to run these reusable exercises in installed versions and collect ordinary
session latency on unrelated projects; this delivery makes that work concrete
without claiming the result in advance.
