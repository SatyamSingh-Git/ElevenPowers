# 84 — a tie is still a result

The runner adoption repair cleared its two controlled installed exercises. That
was a prerequisite, not a coding-quality result. The next step ran the frozen
four-stage queue and order workflows with ordinary and ElevenPowers-assisted
Sonnet 5.5 medium conversations, preserving the same contracts, public tests,
permissions, time policy and every scheduled outcome.

All four conversations finished. Both ordinary arms passed every independent
group at every stage. So did both assisted arms: 4/6/8/10 in each trajectory,
with no observed regression. The final paired differences are zero. Those are
ten distinct final groups per case, not 28 different behaviors per arm. We now
have another completed comparison, not evidence of better code.

The time result is less flattering. Python took 120.899 model-process seconds
ordinary and 283.349 assisted; JavaScript took 88.215 and 167.510. Assisted time
was higher in both. One run per arm cannot isolate the cause or estimate a
population effect, and this is not a production-code performance benchmark.
The measured cost still belongs in the result.

Delivery was mixed. Python used the owned runner in all four turns, retained
five completed calls and receipts, opened four distinct tasks and left its
declared milestones current. JavaScript never produced a qualifying owned call.
Its fresh generic test receipt supports VERIFIED task state, while its exact
declared milestone evidence remains STALE. The source independently passes.
None of those facts makes the others disappear.

We kept JavaScript in the outcome comparison. Excluding it for missing delivery
would select results using an intervention outcome. We also kept the earlier
four failed native trials beside the later two controlled successes. The
producer and exercise matter; one success does not rewrite an older failure or
establish reliable adoption for every project.

The sixteen exported production snapshots reproduce their original grades in
fresh private grading directories. Reproduction needs no model. Raw native
streams, prompts and diagnostics stay private, with bounded public observations
and hashes for the originals. Dirty source snapshots do not acquire a committed
PatchProof subject by being exported.

The next useful step is a no-model investigation of JavaScript's declared-check
gap and native overhead, followed by a generalized repair if the traces justify
one. Another benefit trial needs independently sourced longitudinal cases and a
sampling rule fixed before outcomes. Choosing harder replacements until the
tool wins would answer a different question.
