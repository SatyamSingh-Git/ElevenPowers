JavaScript conversation never did. Both received startup instructions. Better

We kept those results. The next job was to understand the integration gap and

## Look at the actual calls

The original private streams matched their retained hashes. JavaScript combined
source and test writes with `node --test` output filtered through tail or grep.
Those calls can produce generic test evidence, but they do not establish that
the exact configured command completed successfully. A successful outer shell
cannot certify an unobserved child. The fix could not be to call that evidence
owned or to make stale milestones appear current.

Startup already advertised readable owned-runner arguments. What was missing
was a focused reminder at the later generic result, when the exact declaration
was still unqualified. The shared hook now offers that existing entry point.
It launches nothing, adds no completion blocker and makes no stronger evidence
claim. The rule applies to effective project declarations through every host
adapter, without a JavaScript or repository-specific branch.

Actual Python and Node pass/failure controls leave the exact receipt stale until
explicit qualified execution. The reminder is quiet for current exact outcomes,
off, unrelated calls and owned outer envelopes. Task/declaration/configuration
hashes reserve bounded diagnostic intent under the existing ledger lock, after
receipt capture; they do not consume the native result's delivery identity.

The first Python fixture named a `tests` directory. It concealed an existing

Finally, non-command configuration movement did not change its reservation key.

Six new controls failed at those boundaries before repair. The shared predicate

The corrected affected group passed 162 tests. The no-positional pytest control
runs an actual producer; the Vitest case is explicitly an existing parser-fixture

We interrupted the first local full run to repair these witnessed findings.
That partial run remains recorded. An attempted targeted command also named a

the real core test module. Neither attempt becomes a passing qualification.

## Count the work before promising speed

Fresh no-model Stop profiles, with optional strength engines off, took about
2.20 and 2.15 seconds. Each performed seven source snapshots; report rendering
accounted for about 0.61 seconds. Several source-wide receipts were asking the
same read-only report to inspect the repository repeatedly.

The existing freshness context can share an opening source inspection and check
it against a fresh closing one. Human source-backed reports now opt into that
guard. Late same-size edits with restored timestamps, changed configuration,
incomplete scans and expired deadlines refuse green text and remove the earlier
fresh-count claim. File-only reports add no full scan; another report reads again.
No source view spans a command, mutation or Stop execution phase.

The public component reproducer uses fresh 150-file inputs and five source-wide
receipts. Three alternating samples per mode and language-shaped set reduce
source snapshots from five to two. Local medians move from about 0.63 seconds to
0.28–0.29 seconds. Single whole Stop timings change little. We removed repeated
report work; we did not establish a whole-model speedup or faster application.

The one-receipt control exposes a cost rather than a saving: one legacy scan
becomes two to add the closing guard. Its extra timing samples ran during local
qualification load and are kept separate from the earlier measurements. Default
five-receipt work still falls five to two. Sharing is useful when it removes
repeated reads; it is not a promise that every report becomes faster.
