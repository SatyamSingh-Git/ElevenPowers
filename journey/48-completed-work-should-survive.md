# 48 — Completed work should survive

2026-09-29. The automatic setup delivery made verification start without configuration. The next question was whether useful completed work survived a slow second check, a killed hook or another task arriving. The user approved a durable verification runner and requested six detailed pushes, followed by updated documentation.

The implementation remains synchronous. A project OS lock prevents duplicate completion execution. A separate short lock serializes ledger writes, while a progress journal records queued, running, passed, failed, stale, incomplete and deferred checks. Each command persists an incomplete receipt before execution and saves its result before the next command. The same 480-second work deadline covers declared verification, baseline preparation and execution, and targeted confirmation, within the existing 600-second Stop allowance. Commands receive at most 300 seconds and the remaining deadline may shorten that.

The process primitive borrows the repository's existing `eval/live.py` containment: suspend a Windows process, assign it to a kill-on-close Job, then resume. It adds bounded disk-spooled output and descendant cleanup after normal completion as well as timeout and interruption. POSIX uses process groups, which do not contain a process that deliberately escapes. No runtime dependency or background service was added.

Before/after content snapshots bind the result to the inputs that actually stayed in place. A same-length rewrite with a restored old timestamp must be detected, so these boundary snapshots bypass the stat cache. A changed verification declaration invalidates its receipt too. Fresh successful commands are reused even when a separate reproduction obligation remains unresolved; rerunning the same broad suite cannot answer that different question.

The probes changed the implementation. The first killed-owner lock test killed a Windows virtual-environment launcher rather than its actual interpreter; targeting the reported owner PID verified OS lock recovery. Independent review then reproduced declaration reuse after configuration changes, old-task persistence overwriting a new user task, confirmation accepting a historical pass over a later failure, and cached carried-test hashes missing a restored-timestamp rewrite. Those cases gained failing tests and fixes. Targeted confirmation also needed provisional receipts and immediate final persistence, and the ledger's reproduction selection needed to honor the newest outcome without requiring aggregate counters on older named-test receipts.

The real launcher test completed one check, started another, killed the owning hook and restarted it. The completed check stayed saved and was not run again. Frequent status reads exposed a Windows sharing violation during atomic replacement; bounded retries preserve whole-file writes. The journal does not make interrupted work complete: it keeps interruption visible and lets the next ordinary completion reconsider it.

The broad local run passed 914 tests with 26 skips and one compatibility failure. The corrected runner/stress/progress/launcher group then passed 69 tests. CI identified two gaps that the laptop could hide: a test helper used Python 3.12's `rmtree(onexc=...)` while the matrix supports 3.11, and saved B8 analysis tests copied ignored local run files absent from a fresh checkout. The final code part fixes compatibility and supplies minimal analysis input records, with clean-data tests. The final code-head [CI matrix](https://github.com/SatyamSingh-Git/ElevenPowers/actions/runs/36523624912) passed on Ubuntu and Windows with Python 3.11 and 3.13: 916 passed / 31 skipped on each Ubuntu job and 919 passed / 28 skipped on each Windows job. Separate audit checks passed 102 / 2 skipped on Ubuntu and 104 on Windows.

A fresh, read-only Snag fingerprint selected and hashed 4,418 files / 81,841,401 bytes without coverage issues in 55.66 seconds. That is much more work than the earlier 1.11-second selection-only check. It is a single observed timing, not a benchmark or a CI result. The shared deadline is useful precisely because real repository costs differ from small fixtures.

Six parts carry the delivery: journal and ownership; contained processes; immediate receipts and reuse; shared completion and task protection; visible progress, launcher recovery and integration fixes; documentation and the rendered architecture. [The validation record](../docs/validation/2026-09-29-durable-runner.md) identifies the commits and executed checks.

The installed Snag milestone remains open. This delivery proves durable launcher behavior and real-project input coverage, not a full `npm run ci` observed through a live installed Claude Code session. It also does not establish improved patch outcomes, finer dependency invalidation or mutation-based coverage. Those boundaries remain explicit so the next delivery can test a concrete product claim.
