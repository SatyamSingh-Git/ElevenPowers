# 56 — Harder problems still need evidence

The previous comparison had left no bad completion proposal for the plugin to
repair. The user asked for difficult interacting problems and independent
correctness checks, using Sonnet 5 medium or GPT 6.1 medium. The approved bounded
comparison used subscription Sonnet 5 medium: four tasks, two arms, eight minutes
per call. Task size was still not the benefit criterion. A plan, a freshness
check or a completion gate would count if an observed contribution improved
coding; a passing integration alone would not.

We authored four repairs: a durable leased queue with competing SQLite workers,
an asynchronous cache with generation races, an incremental dependency planner,
and a byte stream with transactional checkpoint recovery. Each initial source
carried four planted faults. Correct references passed 94 hidden check groups;
16 single-fault controls were rejected before the model calls. These are
synthetic interaction tasks, not a random sample of difficult real issues.
Literal expectations stayed with the controller rather than the candidate.

Seven calls completed. Every completed first proposal and final patch passed
its frozen groups. Three matched pairs tied on correctness; ordinary guide
completion added fresh exact-command records to the three completed tool runs.
Two pairs were faster with the tool and one was slower. That provides another
receipt result, with no measured patch improvement or established speedup.

The cache tool slot was interrupted when the controller and concurrent local
suite exited abruptly. There was no traceback and the cause remains unknown.
We retained its unfinished code and journal. Instead of replacing the attempt,
an explicit continuation ran only the five slots that had never started. Its
executor identity is separate from the original frozen producer; all eight
approved slots remain in the archive and the comparison remains inconclusive.

Review then showed why a perfect score still needs a boundary. Nested
instruction paths were frozen before a call but omitted from its final seal.
A regression failed before sealing was fixed. The hidden score also did not
execute every added visible test, and its cache shutdown checks missed an old
invalidated fetch pending beside a newer generation. Both blind spots were
reproduced. Changing the frozen evaluator after observing model code would make
the published score ambiguous, so a separately versioned saved-code audit
records these checks and preserves the original scores.

All seven completed final candidates passed that visible audit. The complete
baseline cache closed both old and new fetches correctly. The interrupted tool
snapshot timed out in its visible suite and failed the old-plus-new shutdown
probe. That is a real saved-code defect, not a completed proposal or proof that
the plugin caused it. Omitting it would make this comparison look stronger
than it was.

Twenty-two saved grades reproduced without another model call, alongside the
earlier comparison's unchanged 24. The hosted four-cell Windows/Linux and
Python matrix passed. The task/archive/audit workflow is part of the architecture
and commands guide; public artifacts omit model transcripts and account identity.
See the [dated evidence](../docs/validation/2026-10-02-hard-task-comparison.md)
for every task, timing, interruption and qualification.

Making the contract larger did not produce the desired correctness gain in
the completed pairs. The next evidence step should use representative real
issues and independently check ordinary first proposals, preserving every
success and failure. A claim of coding improvement still needs an observed
improvement, regardless of which ElevenPowers mechanism supplies it.
