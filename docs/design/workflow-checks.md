# Declared workflow feedback and bounded report reads

The matched workflow retained passing JavaScript code with fresh generic task
evidence but stale exact declared milestones. Its actual verification commands
were compound shell scripts and filtered pipelines. Both languages received
startup instructions; Python additionally used the owned runner. Those facts
do not establish why the model chose differently. Source inspection shows no
focused shared follow-up after a generic verification result. No-model profiling
also finds repeated repository scans while rendering the same completion text.

Build on the existing Apache-2.0 runtime: `core.checks.guidance`, command and
evidence qualification, shared native hook transport and `freshness_view`.
The addition is bounded feedback when ordinary verification leaves a declared
check unqualified, plus guarded source-read sharing within a text report.
No additional dependency, shell evaluator or workflow engine is needed.

## Shared feedback boundary

After a completed recognized verification result, identify its corresponding
project-declared property. If that exact declaration's latest receipt is absent,
stale or incomplete, explain that generic evidence has not refreshed the exact
check and show the existing owned entry point. This is advice, with no execution,
claim, stronger verdict or completion blocker. All five native adapters share it.

Keep feedback bounded to one emission per task and declaration/configuration
identity. A current exact receipt, including a current failure, needs no reminder
to establish its execution. Off profile, unrelated/non-command calls, empty
declarations, unknown/interrupted outcomes and owned outer envelopes stay quiet.
Do not turn command prefixes, pipelines, echo trailers or outer success into
exact or owned evidence. Preserve original failure and incomplete receipts and
coalesce existing failure/context messages with the reminder. Readable arguments
and command instructions must remain within the existing context bound.

## Report work and freshness

Only read-only human completion/gate reports with source-wide receipts need
the new shared source inspection. Reuse one operation-scoped fresh source view,
then compare a fresh closing view and configuration before accepting its text.
A moved source/configuration, exhausted deadline or incomplete coverage keeps
the text unverified; same-size edits and restored timestamps do not bypass it.
Retain existing external-input guards and enclosing deadlines. File-only reports
must not acquire an unnecessary full repository scan. Do not cache across calls,
project commands, mutations or tasks, and do not wrap Stop's execution phases
in a stale pre-execution read view.

## Qualification and limits

Use actual unrelated Python/Node commands and native-shaped replay first.
Witness pass, failure masked by an outer success, incomplete execution and
recovery; keep expected generic and declared states distinct. Deterministic
work-count controls must reject repeated source scans and stale closing results.
Measure the same disposable workload before/after with optional engines disabled;
separate report cost from full Stop, inference, native-service variation and
application performance. This does not establish a model speedup or coding benefit.

Preserve every earlier comparison snapshot and outcome. If fresh installed
adoption is needed, use standing Sonnet 5.5 medium subscription authorization
only after current source qualification, with explicit bounded caps, no API
fallback and every incomplete/negative outcome retained. A fresh trial qualifies
its own producer; it does not replace the previous JavaScript failure.
