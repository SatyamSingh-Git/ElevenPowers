# Declared-check completion closure

## Intent

An ordinary task can be `VERIFIED` while an independently configured project
check is absent, stale, incomplete, or currently failing. That distinction is
already preserved in receipts, but it is too easy to miss at completion. The
product must show it plainly without turning a configured check into a new task
obligation or silently executing it.

The second gap is observational. A feedback message can be generated by the
runtime, but a generated string is not proof that a host returned it to the
agent, and a later command is not proof that the agent read or followed it.
The runtime must retain those stages separately and without persisting raw
feedback content or host session identifiers.

## Goals

- Present every supported configured declaration at completion as `CURRENT`,
  `FAILED`, `STALE`, `ABSENT`, or `INCOMPLETE`.
- Base every row on the newest exact declaration/kind/configuration match.
- Keep this completion annex informational: it must not alter the task verdict,
  run a command, add a blocker, or promote a generic receipt.
- Record a feedback intent before output, then record a native host emission
  only after the host response was flushed in a supported context field.
- Report later exact receipts only as a temporal observation after emission;
  never as evidence that an agent comprehended or acted on feedback.
- Use one shared implementation across all host adapters and any project.

## Non-goals

- No project, language, shell-wrapper, or host-specific behavior.
- No model run, transcript retention, new dependency, automatic retry, or
  causal coding-benefit claim.
- No reinterpretation of historical delivery/adoption records.

## Boundaries

`FAILED` means a fresh, completed exact receipt currently reports a failing
result. `STALE` includes an old receipt whose source, configuration, selected
input, or scoped coverage no longer qualifies. `INCOMPLETE` means the latest
exact attempt has not completed or lacks counted test execution; `ABSENT` means
there is no exact receipt. These classifications are not aliases for the task
verdict and do not suppress its existing failure/coverage reporting.

Feedback storage is limited to stable hashes, declared-property names, host,
activation generation, event, timestamp, and hashed session/runtime identity.
Raw feedback, commands, output, prompts, and un-hashed session IDs stay out of
the observation. Missing metadata remains `unobserved` rather than a failed
delivery claim.

## Chosen approach

`core.declared_completion` will be a pure read model used by both completion
text and later diagnostic/report consumers. `core.feedback_delivery` will own
the short-lived prepared emission candidate and durable hashed observations.
`core.check_feedback` keeps deciding whether a generic result leaves an exact
gap; it will register the already bounded text for observation only after its
intent reservation succeeds. Host transport records actual flushes, never
rendering intent or replay-only output as a delivery.
